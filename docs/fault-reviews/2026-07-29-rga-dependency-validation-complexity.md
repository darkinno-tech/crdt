## 1. 问题描述

### 1.1 问题场景

RGA 接收一条含连续 parent 链的 delta，例如大段粘贴产生的连续字符，或在已经很长的文档尾部输入一个字符。

### 1.2 具体表现

旧校验对 delta 中每个节点从 parent 一直回溯，并在每次 `ApplyDelta` 时复制完整的已集成节点和 pending 节点。长链批量 delta 因而可能形成二次遍历；普通单字符编辑也会随历史文档长度产生无关的整图复制。攻击者可以用合法但很深的 parent 链放大 CPU 与堆分配。

### 1.3 错误信息

没有 panic 或错误日志；这是算法复杂度与资源耗尽风险，单元功能测试不会直接失败。

## 2. 根本原因分析

### 2.1 问题分析过程

1. 审查 `text/rga.go` 的 `ApplyDelta`，发现它先把 `nodes` 与 `pending` 合并复制为 `known`。
2. 审查 `acyclicAgainst`，发现它为每个 incoming 节点重新创建 `seen` 并回溯 parent 链。
3. 对连续 parent 链推导最坏复杂度为 `O(k²)`；对已有长文档的一次编辑还会发生 `O(n)` 状态复制。
4. 确认已集成节点具有完整、先前已验证的 parent 闭包；新 cycle 只能经由 incoming 与 pending 依赖图闭合。
5. 据此将冲突检查改为直接查询两张状态表，并使用三色遍历一次性检查 incoming 与 pending 图。

### 2.2 直接原因

`text/rga.go` 的 `ApplyDelta` 为了统一 lookup 创建了整图临时 map，`acyclicAgainst` 又对每个入口独立遍历 parent 链。

### 2.3 根本原因

- **设计层面**：初版重点是允许未知 parent 和拒绝 cycle，没有把 parent 图的增量不变量转化为算法边界。
- **开发层面**：没有对长链 delta 和长文档单字符编辑建立复杂度基准。
- **测试层面**：已有测试覆盖了立即可见的 cycle，却没有覆盖“pending 节点等待的 ID 反向指回 pending 节点”的闭环。

### 2.4 为什么没有提前发现

功能测试用例很小，且先前基准只覆盖字符串读取和 tombstone delta，没有覆盖大段连续插入与增量 append。

## 3. 解决方案

### 3.1 根本解决方案

- 保留有界 `pending` 队列；已集成节点不参与新 cycle 遍历。
- 对 incoming 与 pending 图使用三色 walk，每个相关节点在一次校验中最多访问一次。
- 在做图校验前直接检查 `nodes` 和 `pending` 的 tag 冲突，不再复制完整状态。
- 补充跨 pending 闭环回归、三副本乱序/重复/快照恢复场景和 100,000 节点连续链基准。

### 3.2 影响范围评估

公开 RGA 语义与 v1 wire 形状不变。只改变内部验证工作量和实验协议默认策略：RGA v1 继续要求显式 opt-in，直到完整 tombstone 生命周期得到独立验证。

### 4.1 代码层面

- [x] 不在 `ApplyDelta` 的写锁内进行与 live document 大小线性相关的临时复制。

### 4.2 测试层面

### 4.3 监控层面

- [ ] 宿主应用记录 pending 节点数、pending 字节、资源拒绝数和依赖恢复时长。

## 5. 经验总结

允许乱序依赖不等于允许无界图遍历：把“已验证闭包”和“未解析依赖”分开，才能同时保住收敛正确性与编辑路径的复杂度上限。
