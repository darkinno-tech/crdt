## 1. 问题描述

附件引用协议已经复制对象 ID、声明长度和 SHA-256 摘要，并在文档要求调用方下载后验证；
但包本身没有提供流式校验方法。每个接入方都要自行实现长度和摘要校验，容易遗漏短读、
超长响应或摘要不匹配处理。

## 2. 根本原因分析

### 2.1 问题分析过程

1. 对照 `attachment.Register` 的公开 API、快照恢复和协议文档。
2. 确认元数据验证、合并和帧解码均已落地。
3. 发现文档只写“应用负责摘要校验”，而 `go doc attachment.Reference` 没有可调用的验证 API。
4. 判定这不是对象存储/鉴权缺失：这些属于宿主系统；但字节长度和摘要是引用契约的一部分，
   应由库提供一致且可测试的验证实现。

### 2.2 直接原因

`attachment.Reference` 在 `attachment/register.go` 中只有元数据字段，没有接收
`io.Reader` 的长度与 SHA-256 校验方法。

### 2.3 根本原因

- **设计层面**：初版过度强调“不传输媒体字节”的 CRDT 边界，遗漏了“下载后验证”这一
  不需要拥有存储后端的库内能力。
- **测试层面**：已有测试覆盖协议解码、复制和存储恢复，但没有以真实字节流验证附件引用。

## 3. 解决方案

### 3.1 根本解决方案

新增 `Reference.Verify(io.Reader)`：使用固定 32 KiB 缓冲流式计算 SHA-256，严格比较
读取字节数与 `Reference.Size`，并在短读、超长、摘要错配、读错误或零进展读取时失败。
该方法不选择对象存储、不发起网络请求、不缓存媒体内容，也不处理授权。

### 3.2 验证

- 单元测试覆盖正确对象、短读、超长、内容篡改、空 reader、非法引用、读取错误和零进展读取。
- `FuzzReferenceVerify` 10 秒执行约 518 万次。
- 1 MiB 校验基准约 343–355 µs，4 次分配，约 3.0 GB/s（Apple M4 Pro）。

## 4. 预防措施

- [x] 协议设计评审同时检查“声明的调用方责任”是否需要一个无基础设施依赖的公共 API。
- [x] 对每一个摘要/长度字段补充成功与失败的字节流测试和 fuzz 目标。
- [x] 文档明确 `Reference.Verify` 是下载后、解码前的必经步骤。

## 5. 经验总结（一句话）

> 不持有媒体对象不等于只提供元数据；凡是协议声明的长度和摘要契约，都应提供统一、流式且可测试的验证入口。
