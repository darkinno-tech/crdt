## 1. 问题描述

### 1.1 问题场景

为附件引用注册表补充 LWW 元数据访问器测试时，测试代码新增了 `errors.Is` 和
`reflect.DeepEqual`，但没有同步更新导入列表。

### 1.2 具体表现

首次执行 `go test -cover ./lww ./attachment` 时，`lww` 测试包无法编译；功能代码未被执行。

### 1.3 错误信息

```text
lww/lww_test.go:143:32: undefined: reflect
lww/lww_test.go:161:18: undefined: errors
```

## 2. 临时解决方案

无。问题在本地验证阶段发现，未进入发布流程。

## 3. 根本原因分析

### 3.1 问题分析过程

1. 新增元数据访问器的测试后执行定向覆盖率命令。
2. 编译器明确报出未定义的 `reflect` 与 `errors`。
3. 对照测试体中的 `DeepEqual`、`New`、`Is` 调用确认是导入遗漏，而非包 API 或泛型推断问题。
4. 添加两个标准库导入后重新运行定向测试、覆盖率与 race 检查。

### 3.2 直接原因

`lww/lww_test.go` 使用 `reflect` 和 `errors` 时未在 import 块声明它们。

### 3.3 根本原因

- **开发层面**：在增量补丁中只关注了断言逻辑，没有完成导入闭环检查。
- **流程层面**：首次定向测试发生在多段测试补丁之后，而不是该测试补丁落盘后立即执行。

### 3.4 为什么没有提前发现

Go 的未使用/缺失导入只能在编译阶段诊断；补丁静态检查本身不编译测试文件。

## 4. 解决方案

### 4.1 根本解决方案

在 `lww/lww_test.go` 的 import 块补入 `errors` 与 `reflect`，并立即执行：

```sh
go test -cover ./lww ./attachment
go test -race ./attachment ./lww
```

两项检查均通过；`lww` 覆盖率为 90.4%。

### 4.2 影响范围评估

仅测试文件导入变化，不改变 LWW-Map、附件引用协议或任何对外 wire 语义。

## 5. 预防措施

### 5.1 代码层面

- [x] 每次新增测试辅助函数后立即运行受影响包的编译/测试。
- [x] 提交前运行 `gofmt -w`，使 import 分组由工具统一维护。

### 5.2 测试层面

- [x] 将附件包加入 `make test-unit` 的显式包列表。
- [x] 保留每包 90% 覆盖率门禁，避免新包没有被 CI 覆盖。

## 6. 经验总结（一句话）

> 测试补丁与生产代码一样必须在落盘后立即编译；不要把导入和构建验证留到多个改动之后。
