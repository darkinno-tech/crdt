## 1. 问题描述

### 1.1 问题场景

两个或更多组件在 Go/Wasm API 发布前同时调用 `initRGAWasm`。这在路由切换、多个编辑器挂载或 RGA 与 rich-text 入口同时初始化时可能发生。

### 1.2 具体表现

每个调用都会独立下载、实例化并启动 Go runtime，随后都向 `globalThis.__darkinnoCRDTRGA` 写入 API。最后完成的实例覆盖全局引用；前面调用持有的 API 仍可用，但重复实例增加内存和启动工作，并使全局 API 的归属依赖异步时序。

### 1.3 错误信息

没有线上告警或用户错误日志。本问题由 loader 审计发现；修复前的实现只在函数入口检查一次全局 API，之后每个并发调用都会继续执行 `fetch` 和 `go.run`。

## 2. 临时解决方案（可选）

### 2.1 方案描述

无。未采用调用方互斥或延迟挂载等临时规避，因为它们不能保护库的公共入口。

### 2.2 止血效果

不适用。

### 2.3 临时方案的局限

调用方约束无法覆盖所有懒加载路径，也不能阻止未来组件并发初始化。

## 3. 根本原因分析

### 3.1 问题分析过程

1. 在 TS/Wasm 架构审计中确认 Go runtime 只通过一个全局 API 暴露。
2. 检查 `initRGAWasm` 后发现：全局为空时，每个调用都会自行执行 artifact 拉取、实例化和 `go.run`。
3. 现有真实 Wasm 测试覆盖了协议不匹配、三副本收敛和恢复，但没有首次并发启动的请求数量断言。
4. 新增真实 Go/Wasm 测试同时发起 24 个加载请求，要求服务端只收到一个 artifact 请求，并继续拒绝不兼容协议。
5. 通过模块级共享启动 Promise 串行化第一次启动；启动失败后释放该 Promise，以便下一次调用重试。

### 3.2 直接原因

`initRGAWasm` 的“全局 API 是否存在”检查与实际 `fetch`/实例化之间没有共享的 in-flight 状态，因此并发调用都进入启动分支。

**相关代码位置**：`clients/typescript/src/wasm.ts:348-402`（修复后）。

### 3.3 根本原因

- **设计层面**：把“已启动的全局 API”当作唯一状态，遗漏了“正在启动”的状态。
- **开发层面**：loader 设计验证了单调用协议协商，却没有把页面级并发懒加载纳入状态机。
- **流程层面**：真实 Wasm 测试没有以单次 HTTP 请求数约束共享启动行为。

### 3.4 为什么没有提前发现

- **代码审查阶段**：重点在 frame/Manifest 协商和资源上限，未审查首次加载的竞争窗口。
- **测试阶段**：现有测试均在 runtime 已启动后复用全局 API，无法暴露多个首次启动者。
- **监控告警**：客户端没有 loader 实例数或 artifact 拉取次数指标；本次使用可重复的本地 HTTP 计数测试替代不可靠的线上推断。

## 4. 解决方案

### 4.1 根本解决方案

**修改文件**：`clients/typescript/src/wasm.ts`

增加 `pendingRGAWasmStartup`。当全局 API 尚未发布时，首个调用创建启动 Promise；其余调用等待同一个 Promise，各自再按自身 Manifest 期望验证返回的协议。无论成功或失败，完成方都会清理 pending 引用：成功后后续调用直接使用已发布的 API，失败后允许下一次启动重试。

**测试文件**：`clients/typescript/test/wasm-loader-concurrency.test.mjs:31-46`

测试使用实际 Go/Wasm artifact 和本地 `application/wasm` 服务：24 个并发调用只请求一次 artifact，所有 runtime 的协议一致，随后不兼容协议仍返回 `protocol_mismatch`。

**方案说明**：共享 in-flight Promise 保持现有单全局 API 设计，不引入协议转换或全局锁定。协议校验仍在每个调用返回 runtime 前执行，因此不会因复用启动结果而放宽 Manifest 隔离。

### 4.2 影响范围评估

- 不更改 RGA、packed-v3、legacy v1 或 rich-text 的 frame 字节和 TypeID。
- 首次并发初始化由多实例变为单实例；已启动后的调用行为不变。
- 不兼容 artifact/Manifest 继续 fail-closed。
- 失败启动不缓存，保留网络恢复后的重试能力。

## 5. 预防措施

### 5.1 代码层面

- [x] 全局单例 loader 同时建模 `idle`、`starting`、`ready` 状态，而不是只检查 `ready`。
- [x] 每次从共享启动结果构造 runtime 前重新验证调用方的协议期望。
- [ ] 评审所有新增全局 SDK/Wasm loader 时检查 in-flight 去重和失败后的重试语义。

### 5.2 测试层面

- [x] 保留实际 Go/Wasm 的 24 并发加载、单 HTTP artifact 请求和协议拒绝回归。
- [x] 在 run-v2、legacy v1、packed-v3 artifact 矩阵中执行该回归。
- [ ] 未来若 loader 引入取消或完整性校验，补充超时、失败下载和重试计数用例。

### 5.3 监控层面

- [ ] 产品接入时可记录每页 Wasm artifact 请求数和启动失败码；不得上传文档内容、frame 或身份凭据。

### 5.4 流程/规范层面

- [x] 将首次并发加载纳入 TS/Wasm 发布前的真实场景检查。
- [ ] 代码评审清单增加“共享全局实例的并发启动与失败恢复”项。

## 6. 经验总结（一句话）

> 共享全局 Wasm API 的初始化必须显式覆盖 `starting` 状态，并让每个等待者在复用结果前继续执行自己的协议验证。
