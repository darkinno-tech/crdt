## 1. 问题描述

### 1.1 问题场景

为避免 `StateVector`、`Snapshot` 和重复 `Apply` 在已加载文档上再次编码状态向量，`loadDocument` 需要返回它刚刚重算并校验过的向量。

### 1.2 具体表现

第一次修改把 `actualVector` 声明在 `try` 块内，却在块外的返回对象中引用它。该草稿若运行到含持久化记录的读取路径，会因变量作用域不存在而抛出 `ReferenceError`，使读取/应用请求失败。

### 1.3 错误信息

代码审查在执行测试前发现该控制流：

```text
ReferenceError: actualVector is not defined
```

没有线上告警、用户影响或持久化写入；错误在本地隔离工作树中被拦截。

## 3. 根本原因分析

### 3.1 问题分析过程

1. 审查性能补丁的 `loadDocument` 返回值，确认空记录和已有记录都必须提供 `stateVector`。
2. 沿已有记录路径检查 `try/catch` 的异常清理，发现向量只在 `try` 的词法作用域内声明。
3. 对照块外返回语句，确认 JavaScript 无法解析该标识符；这不是 Yjs 数据问题，也不会被空记录路径覆盖。
4. 将变量提升到函数作用域后，重新执行 Node 真实 Yjs 测试和 Go-to-Node 集成测试。

### 3.2 直接原因

`yjsstore/runtime/server.mjs` 的 `loadDocument` 在块外返回 `actualVector`，但初版补丁在 `try` 内使用 `const actualVector` 声明。

### 3.3 根本原因

- **设计层面**：复用“已验证状态向量”引入了新的函数返回契约，但没有先枚举空记录和已有记录两个控制流。
- **开发层面**：编辑后先做了局部 diff 审查，未立即运行解释器/测试，因此依赖语言作用域检查发现问题。
- **流程层面**：性能改动的审查清单没有显式要求检查新增返回字段在每一条异常与正常路径中都已初始化。

### 3.4 为什么没有提前发现

该错误尚未执行到 Node 测试阶段即由人工 diff 审查发现；原有测试会覆盖已有记录的读取路径，但它不是静态语义检查的替代品。

## 4. 解决方案

### 4.1 根本解决方案

把 `actualVector` 提升到 `loadDocument` 函数作用域，仅在成功物化并完成 persisted-vector 比对后赋值；`catch` 继续销毁文档并返回 `corrupt_store`，正常返回才携带该向量。

**修改文件**：`yjsstore/runtime/server.mjs:355-381`（提交后以实际行号为准）

**方案说明**：这保留了“先重算、再比对、后复用”的顺序，不将磁盘记录中的未经验证向量直接交给调用方。

### 4.2 影响范围评估

仅影响隔离工作树的性能补丁。修正不改变 HTTP 协议、持久化格式、Yjs V1/V2 编码或错误码。

## 5. 预防措施

### 5.1 代码层面

- [x] 对新增返回字段逐分支检查初始化、异常销毁和返回作用域。
- [x] 继续只复用已经从物化文档重算并校验过的数据。

### 5.2 测试层面

- [x] Node 真实 Yjs 全量测试覆盖已有持久化记录的 `Apply`、`StateVector` 和 `Snapshot` 路径。
- [x] Go-to-Node 集成测试覆盖恢复、状态向量和重复提交契约。

### 5.3 流程/规范层面

- [x] 性能补丁在提交前执行 `git diff --check`、语言测试和正常/边界路径审查。

## 6. 经验总结（一句话）

性能优化中复用已校验中间值时，必须先把每个正常与异常控制流的初始化和所有权写清楚，再测量收益。
