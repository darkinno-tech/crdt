# 故障复盘：OR-Set 计数边界与富文本压实错误链不完整

## 基本信息

| 字段 | 内容 |
|------|------|
| 日期 | 2026-08-03 |
| 发现人 | `beta -> preprod` PR #44 的 golangci 门禁 |
| 严重程度 | P1-严重 |
| 影响范围 | OR-Set 不可信帧解码、富文本 tombstone 压实错误映射，以及预发发布门禁 |
| 关联 Issue/PR | #44 |
| 关联提交 | 待本次修复提交生成 |

## 1. 问题描述

### 1.1 问题场景

`beta` 在预发门禁中执行 `golangci-lint`。OR-Set 的解码器会把来自帧的 `uint64` 计数转换为 map 容量，并以 `int` 的 `DecoderLimits` 与计数比较；富文本压实层把底层 `text.ErrUnsafeCompaction` 映射为富文本错误。

### 1.2 具体表现

PR #44 的 golangci job `91520381766` 失败：

```
richtext/tombstone.go:73:5  errorlint
set/orset.go:526:71          errorlint
set/orset.go:553,598,661,... G115
set/orset.go:973:27          unparam
```

这说明代码缺少可机械验证的转换边界；同时 `%v` 会丢失 codec 的原始错误，直接 `==` 只能识别未包装的压实错误。

## 2. 根本原因分析

### 2.1 问题分析过程

1. 读取失败 job 日志，确认失败仅来自 richtext 与 set 的静态安全规则，其他 PR 检查成功或仍在运行。
2. 检查 OR-Set 解码顺序，确认逻辑上先比对 `DecoderLimits` 再预分配，但 `uint64 -> int` 的正确性没有被编码成独立、可审计的 guard。
3. 对比帧包的长度转换和 MoveRGA 的正 int 转换，采用同样的“先验证、再无损转换”模式，而非使用 lint 抑制。
4. 检查富文本错误映射，确认上游可能用 `%w` 包装结构性压实错误，故直接相等比较不满足错误链语义。

### 2.2 直接原因

- OR-Set 在边界检查表达式中混用有符号限制与无符号计数，并在 map 预分配处直接窄化转换。
- codec 错误以 `%v` 格式化，调用者无法用 `errors.Is` 识别根因。
- `richCompactionError` 仅比较错误值，不遍历包装链。
- 测试辅助函数暴露了始终为零的位置参数。

### 2.3 根本原因

- **设计层面**：不可信帧的资源边界没有集中为显式转换契约。
- **开发层面**：功能测试覆盖了超限帧，但未验证错误链和跨位宽容量转换的证明路径。
- **流程层面**：新功能合入 beta 后，完整 lint 首次在预发 PR 的合并候选上暴露问题。

### 2.4 为什么没有提前发现

- 常规单元测试验证了返回失败，没有检查原始 codec 错误是否仍可辨识。
- 64 位本地运行不会自然触发窄化溢出，必须以显式边界测试和静态规则共同覆盖。

## 3. 解决方案

### 3.1 根本解决方案

- 将正 `int` 限制安全提升为 `uint64`，并在每次 map 预分配前验证帧计数可无损转回 `int`。
- 所有计数预算使用 `uint64`，在减法前已经保证不超过总 tag 限制，避免符号混算或下溢。
- codec 与富文本错误均使用 `%w` / `errors.Is` 保留错误链。
- 删除永远为零的测试 seam 参数，并为错误链与转换拒绝路径补回归测试。

### 3.2 影响范围评估

- 不改变 OR-Set 线格式、合法帧的元素顺序或默认资源上限。
- 超限、无效限制、不可表示容量和包装错误均继续 fail-closed；接收端在完整验证前不会替换状态。
- 没有新依赖、网络调用或发布权限变化。

## 4. 预防措施

### 4.1 代码层面

- [x] 对外暴露的错误链保留底层原因。

### 4.2 测试层面

- [x] 增加包装压实错误、codec 原因及计数转换边界测试。

## 5. 经验总结（一句话）

对不可信帧，逻辑上的“已检查”必须落实为独立、无损的转换和预分配证明；错误映射也必须保留可验证的根因链。
