| 关联 Issue/PR | #4；后续发布 CI 已合并 |
| 关联提交 | `18d2f63`（正式 tag 自动化） |

## 1. 问题描述

### 1.1 问题场景

PR #4 合并到 `main` 后，期望自动生成正式版本标签。`beta` 分支此前已生成
`v1.0.1-beta.3`，但 `main` 合并提交 `9d9f3e4` 没有生成 `v1.0.1`。

### 1.2 具体表现

合并后的 GitHub Actions 测试运行成功，但远端只存在 `v1.0.0` 正式标签和
`v1.0.1-beta.1` 至 `v1.0.1-beta.3` 预发布标签。

## 2. 根本原因分析

### 2.1 问题分析过程

1. 检查 `main` 合并提交的 Actions 运行，确认测试、静态检查、覆盖率、容器和
   golangci 均成功。
2. 检查远端 tag，确认预发布 tag 已由 beta 推送生成，正式 tag 未生成。
3. 检查工作流，发现唯一写入 tag 的 `prerelease-tag` job 条件限定为
   `refs/heads/beta`。
4. `main` push 没有对应的正式发布 job，因此即使所有质量门禁通过也不会创建 tag。

### 2.2 直接原因

`.github/workflows/test.yml` 仅定义了 beta 的 tag job，缺少以
`refs/heads/main` 为条件、依赖全部质量门禁的正式发布 job。

### 2.3 根本原因

发布设计只覆盖了 beta 预发布生命周期，未将“PR 合并到 main 后创建正式 tag”
作为独立验收条件与自动化步骤。

### 2.4 为什么没有提前发现

beta job 成功创建预发布标签，验证只覆盖了 beta 分支；没有针对 main 合并事件的
tag 存在性断言。

## 3. 解决方案

新增 `release-tag` job，仅在 `main` push 且所有质量门禁成功后执行。它以最新正式
SemVer 的下一 patch 计算版本，创建带注释 tag；同一提交重试时成功返回，已有同名
tag 指向其他提交时失败，绝不覆盖。

**修改文件**：`.github/workflows/test.yml`

## 4. 预防措施

- [x] beta 与 main 的发布 job 分别使用明确的分支条件。
- [x] 正式发布 job 依赖全部质量门禁并使用独立并发组。
- [x] tag 创建具备幂等和防覆盖校验。
- [x] 在 main Test 运行 `30387664449` 中核对 `v1.0.5` 指向合并提交 `0b6c134`。

## 5. 经验总结

预发布标签成功不代表正式发布链路完整；每个发布分支都必须有可验证的 tag 产出。
