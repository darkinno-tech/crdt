## 1. 问题描述

### 1.1 问题场景

浏览器离线编辑超过配置的追加日志上限后，第二次本地更新已进入内存 CRDT，但 IndexedDB
拒绝追加并返回 `persistence_limit`。调用方已经收到一次 `flush()` 失败，随后仍可能按照常见
资源释放路径调用 `close()`。

### 1.2 具体表现

初版 `flush()` 在抛出后清除了已记录的持久化错误。随后 `close()` 再次调用 `flush()` 时会
成功并释放文档，即使最后一条内存更新从未进入恢复记录。下一次重启可恢复旧状态，形成静默
数据丢失风险。

### 1.3 错误信息

```text
NativeBrowserError: persistence_limit
```

## 3. 根本原因分析

### 3.1 问题分析过程

1. 用 `maxUpdates: 1` 构造有限离线日志，第一条更新执行 `flush()` 成功。
2. 第二条更新使 `MemoryNativeBrowserPersistence.append` 拒绝写入，`flush()` 正确抛出
   `persistence_limit`。
3. 初始测试期望紧随其后的 `close()` 也抛错，但实际关闭成功，说明失败状态被消费而非持续
   保护。
4. 检查异步队列可见 `#reportedPersistenceError` 在 `flush()` 抛出前被设为 `undefined`；
   `close()` 又依赖同一个 `flush()` 作为释放前的恢复屏障。
5. 因此根因是把“向调用者报告失败”错误地实现为“确认失败已处理”，却没有任何 API 表示
   已恢复、已放弃或已导出这条未落盘变更。

### 3.2 直接原因

失败状态一旦被首次 `flush()` 读取即被清空，后续关闭无法再辨识持久化边界未满足。

**相关代码位置**：`clients/typescript/src/browser.ts:280-305`

### 3.3 根本原因

- **设计层面**：把 CRDT 已在内存合并与恢复记录已提交混为一个完成状态。
- **开发层面**：异步队列最初只测试了“失败是否被报告”，没有测试“失败后是否阻止资源释放”。
- **流程层面**：离线上限是有意拒绝而不是可忽略告警，必须把关闭路径纳入安全性验证。

### 3.4 为什么没有提前发现

已有 CRDT 测试覆盖了更新的原子拒绝和乱序收敛，但没有浏览器持久化 facade。首轮 outbox
重试测试只覆盖传输失败；它保留 outbox，却没有模拟存储配额失败后关闭。

## 4. 解决方案

### 4.1 根本解决方案

`flush()` 保留第一个未处理的持久化错误；只要该错误存在，所有后续 `flush()` 和 `close()`
都拒绝，文档、监听器与 store 句柄保持可用，调用方可以显示错误、补齐缺失父节点、重连或
显式处理恢复策略。

**修改文件**：`clients/typescript/src/browser.ts:280-286`

```ts
await this.#persistenceQueue;
if (this.#reportedPersistenceError !== undefined) {
  throw this.#reportedPersistenceError;
}
```

`close()` 在设置 `#closed` 前调用该屏障，因而不会把未确认状态伪装成安全关闭。

### 4.2 影响范围评估

这是更严格的失败语义：此前忽略第一次 `flush()` 异常的调用方可能在 `close()` 再次得到异常。
该变化是有意的；要安全放弃数据需要由产品层提供明确的导出、重置或用户确认流程，而不是
库在关闭时隐式丢弃。

## 5. 预防措施

### 5.1 代码层面

- [x] 持久化失败状态在成功的恢复动作前不得自动清除。
- [x] 任何释放 CRDT/store 资源的路径先经过恢复屏障。
- [ ] 若未来提供“丢弃本地恢复记录”API，必须命名为破坏性操作并要求显式调用。

### 5.2 测试层面

- [x] `clients/typescript/test/browser.test.mjs:178-203` 同时断言超限 `flush()` 与随后的
  `close()` 均返回 `persistence_limit`。
- [ ] 对真实浏览器存储配额/事务中止增加可注入故障适配器和浏览器集成测试。

### 5.3 监控层面

- [ ] 产品适配器应记录 `persistence_limit`、未确认 outbox 数量和连续 `flush()` 失败次数，
  并给用户可见的离线存储提示。

### 5.4 流程/规范层面

- [x] 浏览器客户端文档明确 `flush()` 是本地恢复边界，不能将失败后关闭视为安全。
- [ ] 评审所有新增 outbox/store 时检查“失败、重试、关闭”三条路径是否共享同一确认条件。

## 6. 经验总结（一句话）

> 对本地优先 CRDT 而言，内存合并成功不等于可恢复；持久化失败必须持续阻止安全关闭，直到调用方显式完成恢复或放弃策略。
